# EntityAgent

EclipseLink implements `EntityAgent` against the Jakarta Persistence **4.0.0-M7 draft API**, with Java 21 or later. An agent executes explicit database operations without a persistence context. Read results are detached: changing an object alone does not schedule an update. Call `insert`, `update`, `delete`, or `upsert` to write its state.

```java
try (EntityAgent agent = factory.createEntityAgent()) {
    Order order = agent.get(Order.class, orderId);
    order.setStatus("SHIPPED");
    agent.update(order);
}
```

An entity write without an active transaction completes its own transaction before returning. Inside an explicit transaction, each write executes immediately, while the caller controls commit or rollback. Use a transaction for writes that must commit together:

```java
factory.runInTransaction(EntityAgent.class, agent -> {
    agent.update(firstOrder);
    agent.update(secondOrder);
});
```

Resource-local agents expose `EntityTransaction`. JTA agents join the applicable external transaction and reject `getTransaction()`. Closing an agent does not complete a caller-owned JTA transaction. Typed factory helpers complete transactions they create and close their handler after the callback. A failure escaping a helper marks an existing caller transaction rollback-only.

Query and Statement bulk updates require an active transaction. Queries, native queries, Criteria queries, and stored procedures use the agent's transaction and return detached entity results. Bulk operations do not invoke per-entity callbacks or validation.

For named procedure parameters on PostgreSQL, set the persistence-unit property `eclipselink.jpa.naming_into_indexed` to `true` and register parameters in the procedure's declaration order. This existing compatibility setting preserves public parameter names while using JDBC positions for binding and output retrieval, because the PostgreSQL JDBC driver does not implement the named setter/getter methods. It does not support arbitrary registration order.

The four write-multiple methods process elements in input order and stop at the first failure. They do not create one transaction for the whole list. Without an explicit transaction, successful earlier elements may already be committed. Inside a transaction, the successful prefix remains subject to its eventual commit or rollback.

Insert generates identifiers according to the mapping. Upsert requires an assigned identifier and never generates one, including on a mapping with `@GeneratedValue`. Concurrent conflicting upserts may fail with a persistence or optimistic-lock exception; the provider does not silently adopt a competing version and retry. Agent writes update owned association and collection data, but do not cascade writes to related target entities. Database-write callbacks and configured validation apply to entity operations.

SQL Server assigned-identity upserts require table ownership or the database's existing `ALTER` permission. The insert runs in a prepared server scope so its identity setting does not escape into a later operation or pooled connection borrower.

For Db2, provider-created identity columns use `GENERATED BY DEFAULT` so that generated inserts and assigned-ID upserts can share a mapping. Existing `GENERATED ALWAYS` columns require a schema-owner migration before accepting assigned identifiers. Upsert does not alter the schema or reseed an identity generator; assigned values must be chosen to avoid future generated-key collisions.

Reads include basic state and requested or eager relationships. Unrequested lazy relationships remain unfetched where provider indirection supports them, so a read does not recursively copy an unrelated graph. Loaded state remains usable after the agent closes. Request an entity graph for the relationships needed immediately, or pass an unfetched association or entity reference to `fetch()` on an open agent from the same persistence unit. That agent uses its own transaction, even when the original agent or entity manager has already closed. Unfetched detached state does not retain its original agent or connection and cannot load itself by later navigation. Updating other state leaves unfetched collections unchanged. M7 permits eager fetching where lazy indirection is unavailable. Repeated reads do not reuse entity instances between operations, and changes to returned objects never cause automatic writes. Versioned locked reads retain version checks and references to returned entities, including their loaded relationships, until the relevant obligation is retired or the transaction completes. Closing a cursor does not retire obligations created by consumed rows. Cache `USE` permits the agent to bypass the shared cache; `BYPASS` avoids reading or publishing shared entries. Explicit `REFRESH` fills the cache from a separate database read, after transaction completion when necessary, without publishing caller-owned instances.

The EclipseLink `JpaQuery.getResultCursor()` extension applies the same detached-result and callback rules to each consumed row. Close the cursor when finished; closing its agent also releases the cursor.

Keep the agent open while executing its query, stream, cursor, or procedure objects. Closing it releases owned resources and invalidates those objects. Closing an active resource-local agent rolls back its work. A second successful close is rejected; disposal may be retried after a cleanup failure.

An optimistic conflict alone does not mark a viable agent transaction rollback-only. A database-aborted transaction, connection loss, or incomplete cleanup can prevent further work. Connection-callback exceptions mark an active transaction rollback-only. Preserve the original failure, dispose of the affected agent, and obtain fresh state before retrying. A failed write preserves its prior version when no write succeeded, but failures do not generally restore arbitrary caller fields, consumed generated identifiers, or callback effects. An exception after physical commit cannot undo committed data.

This feature targets a draft specification. Validation applies to the exact API, provider sources, JDKs, databases, and selected TCK tests recorded with a change; it is not a final Jakarta Persistence 4.0 certification claim.
