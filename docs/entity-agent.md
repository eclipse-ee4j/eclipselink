# EntityAgent

EclipseLink implements `EntityAgent` against the Jakarta Persistence **4.0.0-SNAPSHOT draft API**, with Java 21 or later. An agent executes explicit database operations without a persistence context. Read results are detached: changing an object alone does not schedule an update. Call `insert`, `update`, `delete`, or `upsert` to write its state.

```java
try (EntityAgent agent = factory.createEntityAgent()) {
    Order order = agent.get(Order.class, orderId);
    order.setStatus("SHIPPED");
    agent.update(order);
}
```

An entity write without an active transaction completes its own transaction before returning. Inside an explicit transaction, each write executes immediately, while the caller controls commit or rollback. Use a transaction for writes that must commit together:

```java
factory.runInTransaction(EntityAgent.class, agent -> {
    agent.update(firstOrder);
    agent.update(secondOrder);
});
```

Resource-local agents expose `EntityTransaction`. JTA agents join the applicable external transaction and reject `getTransaction()`. Closing an agent does not complete a caller-owned JTA transaction. Typed factory helpers complete transactions they create and close their handler after the callback. A failure escaping a helper marks an existing caller transaction rollback-only.

Query and Statement bulk updates require an active transaction. Queries, native queries, Criteria queries, and stored procedures use the agent's transaction and return detached entity results. Bulk operations do not invoke per-entity callbacks or validation.

For named procedure parameters on PostgreSQL, set the persistence-unit property `eclipselink.jpa.naming_into_indexed` to `true` and register parameters in the procedure's declaration order. This existing compatibility setting preserves public parameter names while using JDBC positions for binding and output retrieval, because the PostgreSQL JDBC driver does not implement the named setter/getter methods. It does not support arbitrary registration order.

The four write-multiple methods process elements in input order and stop at the first failure. They do not create one transaction for the whole list. Without an explicit transaction, successful earlier elements may already be committed. Inside a transaction, the successful prefix remains subject to its eventual commit or rollback.

Insert generates identifiers according to the mapping. Upsert requires an assigned identifier and never generates one, including on a mapping with `@GeneratedValue`. Concurrent conflicting upserts may fail with a persistence or optimistic-lock exception; the provider does not silently adopt a competing version and retry. Agent writes update owned association and collection data, but do not cascade writes to related target entities. Database-write callbacks and configured validation apply to entity operations.

Native descriptor listeners, entity-native callbacks, and descriptor selectors observe the physical insert or update performed by an agent upsert. JPA callbacks and Bean Validation observe the logical upsert operation. The `DescriptorEventListener.preUpsert` and `postUpsert` methods are internal hooks for JPA and validation dispatch. A custom native listener that overrode those internal methods in the initial EntityAgent implementation will now receive its physical insert/update callbacks instead; its internal upsert overrides are no longer called by native dispatch. Both method signatures remain available. Delivering both event families to native listeners would add a new ordering and duplicate-notification contract, so this correction restores physical event delivery only.

SQL Server assigned-identity upserts require table ownership or the database's existing `ALTER` permission. The insert runs in a prepared server scope so its identity setting does not escape into a later operation or pooled connection borrower.

For Db2, provider-created identity columns use `GENERATED BY DEFAULT` so that generated inserts and assigned-ID upserts can share a mapping. Existing `GENERATED ALWAYS` columns require a schema-owner migration before accepting assigned identifiers. Upsert does not alter the schema or reseed an identity generator; assigned values must be chosen to avoid future generated-key collisions. H2 schema generation also uses `GENERATED BY DEFAULT AS IDENTITY`, and generated identifiers are retrieved through JDBC generated keys. These platform choices apply to schemas and inserts used by ordinary entity managers as well as agents.

Upsert currently reads the row before choosing insert or update; it is not a single atomic database upsert statement. Version checks and writes can require further round trips, and the read/write interval permits concurrent races. The write-multiple methods invoke the corresponding operation for each entity, and multiple-ID reads invoke a read for each ID. These implementations do not promise JDBC batching, one SQL statement for the entire input, or a measured performance improvement over an entity manager.

Reads include basic state and requested or eager relationships. Unrequested lazy relationships remain unfetched where provider indirection supports them, so a read does not recursively copy an unrelated graph. Loaded state remains usable after the agent closes. Request an entity graph for the relationships needed immediately, or pass an unfetched association or entity reference to `fetch()` on an open agent from the same persistence unit. That agent uses its own transaction, even when the original agent or entity manager has already closed. Unfetched detached state does not retain its original agent or connection and cannot load itself by later navigation. Updating other state leaves unfetched collections unchanged. M7 permits eager fetching where lazy indirection is unavailable. Repeated reads do not reuse entity instances between operations, and changes to returned objects never cause automatic writes. Versioned locked reads retain version checks and references to returned entities, including their loaded relationships, until the relevant obligation is retired or the transaction completes. Closing a cursor does not retire obligations created by consumed rows. Cache `USE` permits the agent to bypass the shared cache; `BYPASS` avoids reading or publishing shared entries. Explicit `REFRESH` fills the cache from a separate database read, after transaction completion when necessary, without publishing caller-owned instances.

The EclipseLink `JpaQuery.getResultCursor()` extension applies the same detached-result and callback rules to each consumed row. Close the cursor when finished; closing its agent also releases the cursor.

Keep the agent open while executing its query, stream, cursor, or procedure objects. Closing it releases owned resources and invalidates those objects. Closing an active resource-local agent rolls back its work. A second successful close is rejected; disposal may be retried after a cleanup failure.

An optimistic conflict alone does not mark a viable agent transaction rollback-only. A database-aborted transaction, connection loss, or incomplete cleanup can prevent further work. Connection-callback exceptions mark an active transaction rollback-only. Preserve the original failure, dispose of the affected agent, and obtain fresh state before retrying. A failed write preserves its prior version when no write succeeded, but failures do not generally restore arbitrary caller fields, consumed generated identifiers, or callback effects. An exception after physical commit cannot undo committed data.

The shared implementation also changes ordinary `EntityManager` behavior. Applications adopting this draft should account for the following compatibility effects:

- **Validation timing and groups are M7 behavior.** Default validation runs for database insert and update events, and for agent upsert, using `jakarta.validation.groups.Default`. The persist, merge, remove, and database delete events have no default groups; explicitly configured groups still apply to their corresponding events, and an explicit empty group list disables validation for that event. An entity manager therefore normally reports default insertion validation failures when it flushes, or earlier if it performs the database insert earlier. Validation follows user pre-operation callbacks. Removed entities and writes that only increment a lock version do not run update validation. Bulk query and Statement operations continue to bypass entity lifecycle validation.
- **Validation isolation is an EclipseLink deployment choice.** When EclipseLink generates the session name, the validation mode, supplied `ValidatorFactory` identity, and group settings participate in that identity. Factories with different validation configurations therefore use distinct deployments, sessions, and shared caches instead of reusing another factory's listeners. Explicitly assigned session names retain their existing override behavior. Separate provider sessions can allocate separate provider resources; an externally supplied `DataSource` still controls its own physical connection pooling.
- **Graph and lock behavior includes M7 support and bug corrections.** Graph-based find/query operations apply the supplied graph without mutating shared descriptor or named-graph definitions. Pessimistic locking checks an already managed entity's version against the database; refresh intentionally obtains current state instead. The `LockOption` overload now performs a lock rather than accidentally refreshing entity fields. Relationship lock scopes apply to the required related rows, including relationships actually materialized during a `FETCHED` operation, and refresh handles already initialized indirect collections. Ordinary query results remain managed in their entity manager.
- **Native Statement cache invalidation is a provider choice.** A native Statement that changes rows schedules shared entity-cache invalidation and query-cache clearing after successful commit, because arbitrary SQL does not identify the affected entity types. Rollback discards that action, and `CacheStoreMode.BYPASS` suppresses it. Bulk writes do not synchronize previously managed entity instances; applications still need to clear or refresh those instances when appropriate.
- **Shared query corrections also apply to entity managers.** Query configuration and metadata getters that require an open handler reject use after it closes. Per-query hint overrides keep the named template's hint map unchanged. Named references preserve arguments, options, graph names, and result types. Augmented references have no registered name, remain usable after their creating handler closes, and create independent executions in another open handler from the same factory. Converted parameters retain their logical domain type while JDBC procedure registration and null binding use the converter's relational type; conversion occurs once. Constructor and result-set mappings preserve managed results for entity managers and detached results for agents.

The optional `FetchedLockContext` allocation optimization is deferred. An ordinary query nested inside a `FETCHED` operation must mask the enclosing context and restore it on exit. Nested execution of the same query must retain the original context owner so only that owner drains deferred callbacks and closes the token. The current mutable scope's idempotent close also clears its query and previous-scope references, including exceptional exits. A safe no-op path needs a separate immutable representation and focused nesting, failure, and thread-isolation proof; sharing the current mutable scope would be unsafe. No allocation or throughput gain has been measured, and such a path would still call `ThreadLocal.get()` to check for an enclosing scope.

This feature targets a draft specification. Validation applies to the exact API, provider sources, JDKs, databases, and selected TCK tests recorded with a change; it is not a final Jakarta Persistence 4.0 certification claim.
